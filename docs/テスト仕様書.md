# tdb テスト仕様書

本書は [要件定義書](要件定義書.md) の機能要件(REQ-ID)に対する手動確認
テストケースを定義する。tdb は ptrace ベースで実行タイミング・アドレス値
(PIE のロードアドレス、pid 等)に依存するため、本書のテストは自動化
された単体テストではなく、`(tdb)` プロンプトへの入力と出力目視確認による
**手動結合テスト**として記述する。期待結果は「値そのもの」ではなく
「値が満たすべき条件・パターン」で記述する。

## 0. テスト環境準備

### 0.1 ビルド

```sh
cd tdb-linux
cargo build --release
```

`target/release/tdb` が生成されること。警告 (`expr.y` の `UMINUS`
未使用トークン警告)は既知であり無視してよい。

### 0.2 テスト対象サンプルのビルド

| サンプル | ビルドコマンド | 用途 |
| --- | --- | --- |
| `examples/hello` | `gcc -g -O0 -o examples/hello examples/hello.c` | 基本的なブレークポイント/ステップ/式評価 |
| `examples/target` | `gcc -g -O0 -o examples/target examples/target.c` | 構造体/配列/ポインタの整形表示 |
| `examples/thread_target` | `gcc -g -O0 -pthread -o examples/thread_target examples/thread_target.c` | マルチスレッド |
| `examples/fork_target` | `gcc -g -O0 -o examples/fork_target examples/fork_target.c` | マルチプロセス (`fork`) |
| `examples/leak_target` | `gcc -g -O0 -o examples/leak_target examples/leak_target.c` | メモリリーク追跡 |

### 0.3 実行環境

- Linux/x86_64。`ptrace` が許可されていること
  (`/proc/sys/kernel/yama/ptrace_scope` が 0、またはテスト実行ユーザーが
  対象プロセスの親であること。tdb は対象を自ら `fork`/`exec` するため
  通常は追加設定不要)。
- `hello`/`target` は無限ループを含むため、該当テストケースは末尾で
  `kill`/`quit` により明示的に終了させること。

### 0.4 テストケース記法

各テストケースは以下の列を持つ。

| 列 | 内容 |
| --- | --- |
| ID | `TC-<カテゴリ>-<連番>` |
| 対象要件 | [要件定義書](要件定義書.md) の REQ-ID |
| 前提条件 | テスト開始時点の状態 |
| 手順 | `(tdb)` への入力コマンド列 |
| 期待結果 | 出力が満たすべき条件 |

## 1. 実行制御 (EXEC)

前提: `tdb examples/hello` を起動済み(`(tdb)` プロンプト表示)。

| ID | 対象要件 | 前提条件 | 手順 | 期待結果 |
| --- | --- | --- | --- | --- |
| TC-EXEC-01 | REQ-EXEC-01 | 未起動 | `run` | `プロセスを起動しました (pid=..., entry=0x..., PIE)` が表示され、`(tdb)` に戻る |
| TC-EXEC-02 | REQ-EXEC-02 | `break add` 済み・`run` 済み | `continue` | `ブレークポイントで停止: 0x... <add>` の後、`add` を中心としたソース表示(前後最大7行、現在行に `>`)が出る |
| TC-EXEC-03 | REQ-EXEC-03 | `break main` で停止中 | `stepi` | 1命令だけ進み、`rip` が変化する(`info registers` で確認可能。ソース行を跨がないこともある) |
| TC-EXEC-04 | REQ-EXEC-04 | `add` 呼び出し直前の `call` 命令位置で停止中(`main` にブレークし `stepi` を繰り返して `call add` の直前まで進める) | `nexti` | `call` 先(`add` 内部)には入らず、次の命令(戻り先)まで一気に進む |
| TC-EXEC-05 | REQ-EXEC-05 | `break add` で停止中 | `step` | 1行進み、`add` 関数内の次のソース行が表示される(`>` マーカー付き) |
| TC-EXEC-06 | REQ-EXEC-06 | `break main` で停止中、`call add` を含む行の直前 | `next` | `add` 内部には入らず、`main` の次の行まで一気に進む |
| TC-EXEC-07 | REQ-EXEC-07 | `break add` で停止中 | `up` | `add` の呼び出し元(`main` 内の該当行)まで実行が戻り、その位置が表示される |
| TC-EXEC-08 | REQ-EXEC-08 | `run` 済み | `kill` | `プロセスを終了しました` が表示され、以後 `continue` 等は「実行されていない」旨のエラーになる |

| TC-EXEC-10(異常系) | REQ-EXEC-02 | 未起動 | `continue` | 「実行されていません」旨のエラーメッセージが表示され、REPL は継続する(クラッシュしない) |

| TC-WP-07 | REQ-WP-07 | `tdb examples/thread_target`、`break worker` → `run` → `continue`(1スレッド目が到達) | `watch counter` → `continue` | 2つ目のワーカースレッドでの `counter` 書き込みでもウォッチポイントが発火する(スレッドをまたいで監視できることの確認) |

## 7. メモリリーク追跡 (LEAK)

前提: `tdb examples/leak_target`。`examples/leak_target.c` は
`malloc(200)` と `calloc(10, 16)` を意図的に解放しない。この2件は必ず
未解放として検出されるが、実機で確認したところ、glibc/ld.so が起動時に
内部的に確保するメモリ(README「実装の要点」に記載の既知のノイズ)が
`live`/`bad_frees` にあわせて混ざることがあり、`確保回数`/`未解放件数`/
`合計バイト数`は環境(glibc のバージョン等)によって変動しうる。そのため
以下の期待結果は「意図した2件が必ず含まれること」を基準とし、総数・
合計バイト数の完全一致は求めない。

| ID | 対象要件 | 前提条件 | 手順 | 期待結果 |
| --- | --- | --- | --- | --- |
| TC-LEAK-01 | REQ-LEAK-01 | 未起動 | `leak on` → `run` → `continue` | `leak on` のメッセージが表示され、`continue` はプロセス終了まで正常に進む(クラッシュしない) |
| TC-LEAK-02 | REQ-LEAK-02 | TC-LEAK-01 実行後 | `leak` | `on`、確保回数・解放回数・未解放件数が表示される(件数はノイズを含みうるため、`malloc`が最低2回・`calloc`が最低1回分カウントされていることを目安とする) |
| TC-LEAK-03 | REQ-LEAK-03 | TC-LEAK-01 実行後 | `leaks` | 未解放一覧に、`200 バイト  確保元: malloc (leak_target.c:23)` と `160 バイト  確保元: calloc (leak_target.c:24)` の2行が必ず含まれる(それ以外のノイズ行が混ざっていても可) |
| TC-LEAK-04(異常系) | REQ-LEAK-03 | `leak on` していない状態 | `leaks` | 「追跡が無効です」旨のメッセージのみで、クラッシュしない |
| TC-LEAK-05 | REQ-LEAK-05 | `leak on` 済み、`break main` → `run` で `main` 停止中 | `next` を数回実行して `malloc`/`calloc` の呼び出し行をまたぐ | `leak`(または `leaks`)で確認した際、`next` 実行中に通過した `malloc`/`calloc` が捕捉されない(=`continue` 経由のみ捕捉される既知の仕様であることの確認) |
| TC-LEAK-06 | REQ-LEAK-01 | `leak on` 済み | `leak off` → `leak` | `off` と表示され、以後 `continue` してもフックが再設置されない(`info breakpoints` に leak 用の内部ブレークポイントが現れないこと) |

## 11. 合格基準

- 1〜9章の全テストケースが「期待結果」を満たすこと。異常系ケースは
  tdb がクラッシュ(パニック・異常終了)せず、エラーメッセージを表示して
  REPL を継続できることを必須条件とする。
- 10章は制限事項の再現確認であり、症状が文書と一致していれば合格
  (機能追加によって制限が解消された場合は、要件定義書・本書の該当箇所を
  更新すること)。
- テスト実施者は、実行環境(カーネルバージョン、`gcc` バージョン)を
  記録し、アドレス値等の環境依存出力は「条件を満たすか」で判定すること
  (固定値との完全一致を求めない)。
