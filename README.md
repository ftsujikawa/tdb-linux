# tdb

Rust + `ptrace(2)` で作った、Linux/x86_64 向け C プログラム用デバッガの叩き台(たたき台)です。
GDB のような対話コマンドラインで、ブレークポイント設置・実行制御・レジスタ/メモリ閲覧ができます。

シンボル解決には ELF のシンボルテーブル(関数シンボル)を使用しています。
デバッグ情報 (DWARF) があれば `break <func>` でのプロローグ通過位置の判定、
ブレークポイント停止時/`backtrace`でのソース行表示、`step`/`next` によるソース行
単位の実行、`print`/`set` でのローカル変数/仮引数の参照に利用します。
ただし変数の型は整数・ポインタ相当のみに対応し、構造体/配列や、変数の場所式
(`DW_AT_location`)のうちレジスタ・フレームベース相対・絶対アドレス以外の
複雑な形式(ロケーションリスト等)には対応していません。

## 対応環境

- Linux / x86_64 のみ
- デバッグ対象は ELF 実行ファイル (PIE / 非PIE いずれも可)

## ビルド

```sh
cargo build --release
```

## 使い方

```sh
cargo run -- <対象プログラム> [プログラムへの引数...]
# もしくは
./target/release/tdb <対象プログラム> [引数...]
```

起動すると `(tdb)` プロンプトが表示されます。

```
$ cargo run -- examples/hello
(tdb) break add
ブレークポイント 1 を add (0x401136) に設定しました
(tdb) run
プロセスを起動しました (pid=12345, entry=0x401050)
(tdb) continue
ブレークポイントで停止: 0x401136 <add>
examples/hello.c:4
   4	    int c = a + b;
(tdb) print $rdi
$rdi = 0x0000000000000001 (1)
(tdb) print $rdi + $rsi
$rdi + $rsi = 0x0000000000000003 (3)
(tdb) backtrace
#0  0x0000000000401136 in add at examples/hello.c:4
#1  0x0000000000401154 in main at examples/hello.c:11
(tdb) continue
z = 3
[プロセスは終了しました (code=0)]
(tdb) quit
```

解決してブレークポイントを設置します(`*addr` 形式は実行時アドレス決め打ちのため
起動前には使えません)。

## 実装の要点

- `PTRACE_TRACEME` + `execv` で子プロセスを起動し、`waitpid` で停止を待つ。
- ASLR は `personality(ADDR_NO_RANDOMIZE)` で無効化し、PIE バイナリでも
  ロードアドレスを予測しやすくしている。
- 起動時に `signal-hook` クレートでバックグラウンドスレッドを立ち上げ、
  tdb 自身が SIGINT (Ctrl-C) を受け取ったらデバッグ対象プロセスに SIGINT を
  転送する。これにより、`continue` 等でデバッグ対象を実行中に Ctrl-C を
  押すと、tdb 自身はデフォルトの「終了」動作をせずに動き続け、デバッグ
  対象は ptrace 経由でシグナル停止として捕捉され、通常のシグナル停止
  (`シグナル SIGINT を受信して停止しました`)として `waitpid` に報告される
  (GDB で `continue` 中に Ctrl-C を押すのと同様の体験)。現在実行中の
  デバッグ対象の pid はプロセス全体で共有する `static AtomicI32` に保持し、
  転送スレッドがそこから読む。
- PIE バイナリの実ロードアドレス(バイアス)は `/proc/<pid>/maps` を読んで検出。
- `syms` は ELF の `.symtab`/`.dynsym` から読み取った関数シンボル一覧
  (`break <func>` や `backtrace` のシンボル解決に使っているものと同じ)を
  そのまま表示する。引数を渡すとシンボル名にその文字列を含むものだけに
  絞り込む(部分一致、正規表現ではない)。プロセス実行中はロードバイアスを
  加えた実行時アドレスを、未実行なら ELF 上のリンク時アドレスをそのまま
  表示する。
- `lines` は `.debug_line` の行テーブル(`break`/`step`/ソース行表示に使って
  いるものと同じ)をアドレス昇順にそのまま表示する。引数を関数名として
  解決できれば(`syms` と同じ ELF シンボルテーブル参照)、その関数のアドレス
  範囲内の行だけに絞り込む。終端マーカー(`end_sequence`)の行は実際の
  ソース行ではないため表示しない。アドレス表示は `syms` と同様、実行中か
  どうかで実行時/リンク時アドレスを切り替える。
- ブレークポイントは対象アドレスの先頭バイトを `0xCC` (`int3`) に書き換える
  古典的なソフトウェアブレークポイント方式。ヒット時は `rip` を1つ戻し、
  元のバイトへ戻してシングルステップしてから再度 `0xCC` を書き戻す。
- `nexti` は先頭の call 命令 (`E8 rel32` および `FF /2`,`/3` の間接呼び出し) を
  簡易デコードし、戻りアドレスに一時ブレークポイントを置いて `continue` する。
  他の命令は通常の `stepi` と同じ。
- `up` は `rbp` チェインから呼び出し元の戻りアドレス (`*(rbp+8)`) を求め、
  そこに一時ブレークポイントを置いて `continue` する (`nexti` と同じ方式)。
  `backtrace` 同様、フレームポインタを前提にしている。
- シンボル解決は ELF の `.symtab`/`.dynsym` の `STT_FUNC` エントリのみを使用。
  `backtrace` は `rbp` チェイン(フレームポインタ)を前提にしており、
  `-fomit-frame-pointer` でビルドされたバイナリや関数プロローグ実行前の
  停止位置では正しく辿れないことがある。
- `break <func>` は関数の先頭ではなく、プロローグを通過した位置にブレークポイント
  を設置する。`.debug_line` があれば GDB と同様に行番号が変化する最初の行の
  アドレスを使い、無ければ `endbr64`/`push rbp`/`mov rbp,rsp`/`sub rsp,N` という
  典型的なプロローグ列を命令デコードして判定する(`gimli` でパース、`iced-x86` で
  デコード)。パターンに一致しない場合は関数先頭のままとなる。
- ブレークポイントで停止した際、`.debug_line` から該当アドレスのソースファイル/
  行が分かればその行を表示し、分からなければ(デバッグ情報なし、ソースファイルが
  手元にない等)`iced-x86` でその場を1命令だけ逆アセンブルして表示する。
- `step` は `.debug_line` の行テーブルを使い、行番号が変わる `is_stmt` 行に
  達するまで機械語命令を1つずつ実行する。`call` 命令もそのまま1命令として
  実行されるだけなので、呼び出し先へ自然にステップインする。ステップ先が
  `.debug_line` でカバーされていない(共有ライブラリ等、デバッグ情報のない)
  コードの場合は、`call` 直後のスタックトップにある戻りアドレスに一時
  ブレークポイントを置いて `continue` し、呼び出し元に戻ってから行単位の
  ステップを続ける。
- `next` は `step` と同様に行単位で進むが、命令列を見て `call` に差し掛かった
  ことを検出した場合は呼び出し先には入らず、戻りアドレス (`nexti` と同じ
  `call_instruction_len` によるデコードで算出) に一時ブレークポイントを
  置いて `continue` することでまるごと実行する。呼び出し先の中でユーザーが
  設置した実際のブレークポイントに当たった場合はそこで停止する。
- `print`/`set` は自前の再帰下降パーサ (`src/expr.rs`) で式を評価する。
  レジスタ参照 (`$rax` 等)、ローカル変数/仮引数名 (`x` 等、DWARF情報が必要)、
  10進/16進(`0x`)整数リテラル、`3.4` のような浮動小数点リテラル、四則演算・
  剰余、ビット演算 (`& | ^ ~ << >>`)、単項 `-`、アドレス取得 `&<変数名>`、
  `()`、メモリ参照 `*<addr式>` (8バイト読み、常に整数)に対応する。
  `*` は直前に値が来ていれば乗算、そうでなければデリファレンスとして解釈し、
  同様に `&` も直前に値が来ていれば(ビット)AND、そうでなければアドレス取得
  として解釈する(`parse_unary`/`parse_and` の位置で判別、`*` と同じ方式)。
  `&` はローカル変数/仮引数名にのみ使え(`&x` の直後は識別子である必要が
  あり、`&5` や `&$rax`、`&(x)` はエラー)、その変数の実体アドレスを返す。
  `*` は型情報を持たない生アドレスへの参照のため常に8バイト読みであり、
  例えば `*&x` で `x` が4バイトの `int` の場合、`x` の値だけでなく隣接する
  8バイト全体を読んでしまい元の値と一致しない(この点は `*` 単体の既知の
  制約で、`&` の追加により新たに生じたものではない)。
  演算はどちらかのオペランドが浮動小数点数なら両方を f64 に昇格して計算し、
  ビット演算・デリファレンス・アドレス取得は整数のみに対応(浮動小数点数を
  渡すとエラー)。
  `set *<addr式>=<式>` のメモリ書き込みは(コードパッチ用途を想定し)従来通り
  1バイト単位(浮動小数点数の場合は整数に切り捨ててから書き込む)。
  `set <変数名>=<式>` はローカル変数/仮引数の実体アドレスに、変数の型サイズ
  (`DW_AT_byte_size`、最大8バイト)ぶんだけ書き込む。変数の型が `float`/
  `double` (`DW_ATE_float`) の場合は値を IEEE754 のビット列 (4バイトなら
  `f32`、それ以外は `f64`) に変換して書き込み、代入する式が整数であっても
  自動的に浮動小数点数に変換する。変数の型が浮動小数点数でない場合、代入する
  式が浮動小数点数であれば整数に切り捨てる(C の暗黙変換と同様)。
  `set` の代入先の判定順は `*` プレフィックス(メモリ) → `$` プレフィックス
  (レジスタ) → `->` を含むかどうか(構造体メンバ) → それ以外は変数名、
  というシンプルな優先順位。
- `->` による構造体メンバアクセス (`a->b`, `a->b->c` のような連鎖も可) に
  対応する。連鎖の先頭は DWARF 型情報が必要なため裸の変数名でなければ
  ならない(`(x)->f` や `$rax->f` は不可)。`->` の左辺が構造体へのポインタ
  なら実際に指す先を、構造体そのものであればその実体をそのまま辿る(この
  ツールでは `->` と `.` を区別せず、後者の記法は提供していない)。
  `.debug_info` の `DW_TAG_structure_type`/`DW_TAG_union_type` と、その
  直下の `DW_TAG_member` (名前・`DW_AT_data_member_location`・型)を解決して
  実現しており、構造体がポインタ経由で自分自身を含む場合(連結リスト等)の
  無限再帰を避けるため、型解決の再帰は16段で打ち切る(通常の `->` の連鎖が
  そこまで深くなることはまず無い)。最終メンバの型が整数/浮動小数点数/
  ポインタであれば値を読み書きできる。最終メンバが構造体そのものの場合
  (例: `p->pt` で `pt` が構造体を値として持つメンバ)は、`->` 経由では
  先頭8バイトを整数として返すのみ(後述の構造体整形表示の対象外)。
- `print <変数名>` で式全体が単一の変数名(`->` を含まない)の場合に限り、
  その変数が構造体型であれば `{a = 1, b = 2}` の形式で整形表示する。
  ポインタ型メンバは指す先を辿らずアドレスの16進表示のみ行う(ネストした
  構造体は再帰的に展開する)。`print p->pt` のように `->` 経由で構造体に
  辿り着いた場合や `print *p`(ポインタの指す先)は、この整形表示の対象
  にはならない(前述の通り整数として読まれてしまう)。
  `set print pretty on` の場合は複数行インデント表示になり、加えて構造体
  自身とすべてのメンバに型名を付記する(例:
  `a = (struct Node) {\n  value = 10 (int),\n  pt = (struct Point) {...},\n  next = 0x... (struct Node *)\n}`)。
  型名は `DW_TAG_base_type`/`DW_TAG_structure_type`/`DW_TAG_union_type` の
  `DW_AT_name` から取得し、無名構造体/共用体は `struct`/`union` とだけ表示
  する。`pretty off`(既定)では型名は表示しない(従来通り値のみ)。
- `set print pretty on` の場合、式全体が単一の変数名またはそのアドレス取得
  (`print y`, `print p`, `print &y`)で型が分かるときは常に型情報を付記する:
  ポインタ型は `(型名)0xアドレス`(例: `y` が `int` なら `&y` は
  `(int *)0x7fffffffd50c`、`p` が `int *` なら `&p` は `(int **)0x...`)、
  それ以外の型(整数・浮動小数点数等)は `(型名)値`(例: `y = (int)4`、
  `w = (double)2.5`)。レジスタ参照・リテラル・演算を含む式など、静的な
  型情報を持たない場合は `pretty on` でも型情報は付かない(型不明のまま
  なので付けようがない)。`pretty off`(既定)では従来通り型情報を表示せず、
  ポインタは `0x...018x (10進)`、非ポインタは値のみ。
- `print` の表示形式は式全体が単一の変数名の場合のみ型に応じて変える:
  ポインタ型なら16進+10進 (`0x... (n)`)、それ以外の型(整数等)なら10進のみ。
  レジスタ参照・リテラル・演算を含む式など、静的な型情報を持たない場合は
  従来通り16進+10進の両方を表示する。
- `print/fmt`(`p/fmt`, `print /fmt` のようにスペースを挟んでも可)で表示形式を
  明示的に指定できる。指定した場合は上記の型に応じた自動判定より優先される。
  `x`=16進(`0x...`)、`o`=8進(`0...`)、`t`=2進、`d`/`i`=10進、`c`=1バイトを
  文字として(例: `65 'A'`。非表示文字は `'\xNN'`)、`s`=値をアドレスとみなし
  ヌル終端文字列として読む(最大バイト数は `set print elements`、既定200。
  UTF-8として解釈できない場合は置換文字が入る)。浮動小数点数の式に整数系
  フォーマットを指定した場合は整数に切り捨てて扱う。構造体の整形表示に
  フォーマット指定 (`print/x structvar` 等) は使えない(エラーになる)。
- GDB の `set print`/`show print` サブコマンド群のうち、代表として
  `pretty`(構造体の複数行表示、既定 off)と `elements`(文字列/構造体表示の
  要素数上限、既定 200、`unlimited` で無制限)のみをサポートする。GDB 本家に
  ある他のオプション(`address`, `null-stop`, `union` 等)には対応していない。
- `show locals`/`show args` は現在の PC を含む関数 (`DW_TAG_subprogram`) の
  `DW_TAG_variable`/`DW_TAG_formal_parameter` を、`show globals` はコンパイル
  単位直下(関数の外)で宣言された `DW_TAG_variable` を、それぞれ `名前 = 値`
  の形式で列挙する。表示形式は `print`/`set print pretty` と同じルールに
  従う。関数ローカルな `static` 変数(関数の中にあるが静的記憶域を持つ変数)
  は `show locals`/`show globals` のどちらにも現れない(このツールでは
  「関数の外で宣言されているか」だけでグローバル/ローカルを区別する単純化
  のため)。
- 変数名は `.debug_info` の DIE ツリー (`DW_TAG_subprogram`/`DW_TAG_variable`/
  `DW_TAG_formal_parameter`/`DW_TAG_lexical_block`) を辿り、現在の PC を含む
  関数のスコープ内から名前で検索する(他の関数のローカル変数は見えない)。
  変数の位置は `DW_AT_location` の DWARF 式を評価して求め、`DW_OP_fbreg`
  (フレームベース相対)、`DW_OP_addr`(絶対アドレス、グローバル変数用)、
  `DW_OP_bregN`(レジスタ相対)に対応する。フレームベース (`DW_AT_frame_base`)
  が `DW_OP_call_frame_cfa` の場合は CFI を読まず、`push rbp; mov rbp,rsp`
  という典型的なプロローグを前提に `rbp+16` で近似する(`backtrace`/`up` の
  rbp チェイン前提と同様の簡略化)。型は `DW_TAG_base_type`(整数、符号の
  有無を判定)と `DW_TAG_pointer_type` のみ解釈し、構造体・配列・共用体等は
  対応していない。

## 既知の制限(たたき台であることの注記)

- 変数表示は整数・ポインタ相当の型のみ対応(構造体・配列・共用体等は不可)。
  また `DW_AT_frame_base` が `DW_OP_call_frame_cfa` の場合、CFI
  (`.debug_frame`/`.eh_frame`)は読まず `rbp+16` で近似しているため、
  フレームポインタを省略したビルド (`-fomit-frame-pointer`) や、関数の
  プロローグ実行前の停止位置では変数の値を正しく読めないことがある
  (`break` は既定でプロローグを通過した位置に止まるため通常は問題にならない)。
- 共有ライブラリ(libc など)のシンボルは解決しない。バックトレースが
  ライブラリ内に入ると `??` と表示される。
- ハードウェアブレークポイントやウォッチポイントは未実装。
- マルチスレッドプログラムは想定していない(単一スレッド前提)。
- `nexti` の再帰時の戻り先ブレークポイントはフレーム識別をしていないため、
  再帰呼び出し中に同じ戻りアドレスへ複数回ヒットしうる。

## サンプル

`examples/hello.c` に簡単な検証用 C プログラムを同梱しています。

```sh
gcc -g -O0 -o examples/hello examples/hello.c
cargo run -- examples/hello
```
